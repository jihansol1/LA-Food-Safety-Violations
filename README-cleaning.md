# Inspection data preparation

This addition prepares inspection-level outcomes for the food-safety ML project.
It does not train models or construct historical predictors. Original CSVs remain
in `data/raw/inspections.csv` and `data/raw/violations.csv`.

## Run

From the project root, using Python 3.10 or later:

```bash
python -m pip install -r requirements-cleaning.txt
python src/prepare_data.py
python -m unittest discover -s tests -p 'test_prepare_data.py' -v
python src/verify_cleaning.py
```

The script also accepts `--raw-dir`, `--output-dir`, and `--report-dir`.
Use `reports/cleaning_report.md` and `reports/cleaning_summary.json` for the actual
counts, label prevalence, source hashes, and decisions from the latest run.

## Processed tables

| File | Use |
|---|---|
| `data/processed/inspections_clean.csv` | All inspections with normalized metadata, aggregate outcomes, and quality flags |
| `data/processed/violations_clean.csv` | All original violation records, with classifications, source-record numbers, duplicate flags, and join flags |
| `data/processed/routine_restaurant_inspections.csv` | All routine restaurant inspections, including unresolved cases with blank labels |
| `data/processed/modeling_cohort.csv` | Conservative, complete-label routine restaurant cohort for subsequent feature engineering |

Labels `y_major`, `y_minor`, and `y_grp` indicate the presence of scored violations
at that inspection. They are outcomes, not historical predictors. The cohort is
not ready for model fitting until predictors and chronological partitions exist.
Uncertain labels are blank in master tables; do not fill them with zeros.

Counts reflect recorded violation rows, including repeated rows. Repeated exact
rows are retained because removing them usually breaks agreement with recorded
inspection scores. Administrative entries and multiple-major penalties are kept
separate. Unsupported code/point/status combinations are flagged, not corrected.

The original score remains authoritative metadata; mismatches with recorded
points are reviewed and conservatively excluded from the main cohort. Inspections
with score 100 and no linked violation records are retained as inferred negatives,
with an explicit flag and documented assumption.

Both observed retail-food code versions (F0xx and F1xx) are mapped. This is a
project rule based on the source code descriptions and scoring framework, not a
claim that every future code has been validated. Review the mapping audit after
changing data snapshots. Zero-point substantive observations are unresolved,
rather than assumed to indicate no violation.

## Audit outputs

- `violation_review_queue.csv`: unsupported or contradictory records.
- `inspection_review_queue.csv`: inspections affected by label or metadata issues.
- `orphan_violations.csv`: violation rows with no matching inspection.
- `repeated_violation_records.csv`: repeated rows retained in the source data.
- `duplicate_score_reconciliation.csv`: point totals with and without repeats.
- `violation_mapping_audit.csv`: code, description, status, points, and mapping frequencies.
- `monthly_cohort_statistics.csv`: inspection and positive-label counts by month.
- `label_combinations.csv`: counts of the eight possible label combinations.
- `source_spot_checks.csv`: independent checks against raw rows, generated by `verify_cleaning.py`.

The program key combines facility ID and record ID. Distinct health programs at
the same facility are not merged. ACTIVE/INACTIVE status does not filter history.
Keep employee IDs, names, target scores, grades, and violation outcomes out of the
feature list unless a separately justified historical construction makes them
available at prediction time. Date, score, and target labels in this table do not
by themselves define a valid future-prediction dataset.
